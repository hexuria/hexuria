The Portable Agent Toolchain

Agents shouldn't just use computers. They should build their own.

Hexuria is building the Portable Agent Toolchain that lets AI workers acquire, verify, install, permission, execute, update and replace their own software without rebuilding their entire computer.

The problem

Humans still build the computer.

Most agent infrastructure still looks like this. A person assembles an image, installs everything the agent might need, and hands the result over.

  1. Human
  2. Build the container
  3. Install everything the agent might need
  4. Agent

Then the job changes. The worker needs Postgres, ffmpeg, a compiler, a document processor, another CLI, an MCP server, or an internal tool. A person edits the image, rebuilds it, redeploys, reinstalls, reconfigures, and often restarts the service.

That is tolerable for a handful of agents. It is the wrong operating model for a population of specialized workers.

Why this breaks

Specialization does not share one image.

Each worker can have a different job, different tools, different permissions, different models, and a different security boundary. A new capability should not mean a new machine.

100Already too many images to babysit by hand.
10,000Rebuilds become the job. The agents wait.
1,000,000A human in the rebuild path is not an architecture.

Those figures are the scaling argument. Hexuria does not claim to operate a million agents.

A million agents cannot wait for a million Docker rebuilds.

The insight

Software for software workers.

People install the software their job needs. Developers install Git, compilers, databases, and CLIs. Designers install design tools. Operations teams live in CRMs and spreadsheets. AI workers will need the same specialization.

Provisioning those environments by hand does not scale. The long-term move is an agent that can tell the difference between “I need capability X” and “rebuild my computer,” and then do this safely:

  1. discover
  2. verify
  3. request permission
  4. install
  5. execute
  6. retain or remove

The computer becomes adaptive to the worker. That lifecycle is the product. A chat window is not.

The toolchain

Don't rebuild the computer. Install the capability.

A Portable Agent Toolchain sits on the worker’s existing harness. It is how capabilities are discovered, acquired, checked, allowed, installed, run, watched, updated, and taken away. It is not a second agent runtime.

  1. Discover
  2. Acquire
  3. Verify
  4. Authorize
  5. Install
  6. Execute
  7. Observe
  8. Update
  9. then
  10. Rollback
  11. Revoke
  12. Remove

Capabilities should be independently shippable software. Versioned, isolated, and replaceable, without baking them into one image.

MCP

Answers what tools this model can call. Useful. Hexuria uses it. A plugin can bring MCP servers.

Portable Agent Toolchain

Answers what software this agent can own and operate. Calling a tool and owning a capability are different. Owning requires the lifecycle above.

MCP tells an agent what tools it can call. The Portable Agent Toolchain tells it what software it can own.

What is on main today is narrower than this picture. OpenGrok loads agent plugins as folders of skills and MCP servers, with a trust distinction: unverified tools ask a person first. A pinned, per-account catalog install is not on main yet. Wasm and remote providers are not a shipped plane. The lifecycle is the design the repositories are growing into, not a finished product.

The execution plane

The toolchain sits above the provider.

One capability router. Several execution providers. The router picks the provider the capability needs. Providers are not interchangeable, and a container does not go away because a smaller unit exists.

This is not “WASM replaces Docker.” Both belong. A full computer, when the job is a computer. A composable capability, when the job is one new piece of software. Do not rebuild an entire computer when the agent only needs one new capability.

OpenGrok already attaches a Docker computer per coworker and can reach a machine the person enrolled. There is no Wasmtime or Wasmer executor in these repositories. Local execution here means enrolled machines and the Box guest, not a general capability router.

A composable computer

A base, then only the pieces the job needs.

The industry default is one prebuilt computer with the union of every tool any worker might touch. The other option is a base plus capabilities that can be added, removed, updated, isolated, versioned, and verified on their own.

Portable

The model is replaceable. The worker remains.

A capability is a shippable unit. The worker can acquire it, move it, and run it without rebuilding the whole computer. It has identity, and a lifecycle the harness can recover.

The system should be able to say, for each capability:

  • WhatWhat is installed, and why.
  • VersionWhich version, and where it came from.
  • TrustWhether it was verified, and by what check.
  • WhoWhich agent may use it.
  • RightsPermissions, credentials, and which runtime executes it.
  • LimitsWhat it may consume.
  • ChangeHow it is updated, rolled back, or revoked.
  • TraceWhat happened during execution.

A capability should survive the model turn that installed it, a change of model, a closed window, and a worker restart where that is the right semantic. It should not have to be reconstructed from the prompt.

OpenGrok already keeps the harness outside the tab: turns, tool results, cancellation, retries, and replay live on the server. NativeChat is a window onto that. Extending the same record to every acquired capability is the toolchain’s job, and it is not finished.

Authority

Autonomy without a boundary is just execution.

Autonomy without authority boundaries is not autonomy. It is uncontrolled execution.

Before an agent acquires or runs software, something has to be able to reason about identity, provenance, filesystem, network, credentials, compute, money, a human yes, and revocation. Authorization is part of the toolchain, not a settings screen added later.

What exists now is the harness gate, not a separate authority product. OpenGrok’s consent model is on main: block refuses, ask raises a card a person can answer, allow proceeds, and unverified plugin tools ask every time. There is no shipped product here that prices an install, escrows a credential for a new capability, or revokes one across providers.

That broader authority layer is planned. It is not a repository we are willing to point at yet.

Verification

Acquire nothing you cannot stand behind.

  1. Capability
  2. Provenance
  3. Verification
  4. Authorization
  5. Execution

Depending on the capability, a check might be a signature, a checksum, tests, static analysis, a security policy, fuzzing, a runtime restriction, or a person. Those are possible mechanisms. They are not all built, and a bounded check is not a proof.

impeccable-rust is the verification practice in public code: an agent skill that picks a verifier for the failure that can actually happen, and reports the bounds and the blind spots. It does not mean every capability in the toolchain is signed, fuzzed, or proved.

One stack

Pieces of one toolchain. One lifecycle.

OpenGrok owns the harness: the agent loop, tool calls, results, cancellation, retries, persistence, replay, permissions, failures, and state. The toolchain extends what that same worker can acquire and execute. It does not stand up a second orchestrator beside it.

Models provide intelligence. The toolchain gives intelligence somewhere to work. The gateway routes models. It is not the headline.

  • NativeChat Shipped

    The human window. Login, coworkers, turns. It does not call model providers and it does not hold API keys.

  • open-ai-gateway Shipped

    One door for model calls an organisation already makes. Routing and credentials. A piece of the stack.

  • Box Shipped

    The full-computer provider: a Linux guest, exec and files over HTTP, a desktop. Not the control plane.

  • impeccable-rust Shipped

    Verification skill for agent-written Rust. Honest bounds. Not a universal prover.

  • gpui-agent Experimental

    In-process control plane for GPUI apps that embed it. Semantic snapshots and scripted actions. Not a computer, and not CDP.

  • reverse-web-mcp Experimental

    Web capability research: compile an app’s actions into a plan and a receipt. Not the toolchain’s web provider.

The outcome

Persistent AI coworkers.

A coworker is what you get once the toolchain is real: a worker that keeps its tools, its computer, its permissions, and its harness when the model changes and when the window closes.

One worker. Its own tools. Its own computer. Its own permissions. Its own harness.

Persistent coworkers are the outcome. Portable capabilities are how they get there: install the piece, do not rebuild the machine. From static sandboxes to self-maintaining agent computers.

NativeChat and OpenGrok already keep work on the server after the tab closes. Self-maintaining computers are still ahead of the code.
